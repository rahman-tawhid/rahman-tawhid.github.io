Building a Loop and Graph Runtime for Agents

Seven layers, in the order I built them, the question each one had to settle, and the alternatives I set aside along the way.

Tawhid Rahman is the CEO of Softograph, a software company he founded in 2012. He designed and built the loop and graph runtime that his own multi-agent system runs on, including the development setup he works in every day.

Tawhid Rahman 2026 ~24 min read

The first runner I wrote for my agents was a for loop over a list of strings. It read a project brief, looked up an archetype in a hardcoded table, and ran the agents in order, each one handing its output to the next. It worked the way a conveyor belt works. Nothing on it could fork, nothing could go back, and nothing checked whether the agent that had just finished did what it said it did.

The runner I use now walks a graph. A node can be a single agent, a loop that retries until a verifier passes it, or a whole sub-graph with its own plan. Edges carry guards, joins wait for every branch, and a job starts gated and moves toward autonomy one level at a time, on evidence. The field has started calling this shape graph engineering, and the name fits. What the name leaves out is that the diagram was the smallest part of the work.

The picture of nodes and edges came together quickly. The rules around it took most of the effort, and each serious bug I found lived in those rules rather than in the walk. So this is the build in the order I did it. Each section names the question a layer had to answer, the architecture I settled on, and the alternatives I weighed and set aside. The set-aside options matter as much as the chosen ones, because most of them looked reasonable at the time.

Audit the runner first

Before designing anything new I read the old runner the way a verifier would, asking what it believed and why it believed it. Four findings came back, and none of them would have shown up on a diagram.

The first was that status was self-reported. An agent printed a JSON block, and the only check was that four fields had the right JavaScript types. An agent that wrote nothing and printed {"status":"complete"} was recorded as complete, and on resume it was skipped forever. The second was worse. needs_review, the status the executor assigned when it could not parse any output at all, was counted as success.

The third was the retry loop. It terminated on the agent's own status and, on a retry, fed the agent its own failure summary as the reason. Attempt three could not be told apart from attempt one. The fourth was drift. Five agents in the registry document were unmoored from any definition file, and the router deleted them without complaint, so a six-agent pipeline ran as one agent and five console warnings.

A graph drawn on top of that runner would have entrenched those claims at every fork and join. That fixed the build order before anything else did.

Build order. Solid boxes carry the ones above them. Dashed boxes were attached once the graph existed. Autonomy is blocked on the verifier, because a slider built on self-reported success promotes jobs on the agent's own word.

One rule held across every stage of the build. Every test that existed before a change had to pass after it with zero edits, and every new field on an existing interface had to be optional, with its absence meaning the old behaviour. The suite grew from 185 tests to 491 across the loop and graph work. The rule mattered more than the count, because a test that needs editing means the seam moved further than the change required. It was broken once, on purpose, and I come back to that in the registry section.

1. The harness seam

The question: where does the boundary between “what to run” and “how to run it” sit?

The old executor built a shell command in a template literal, claude --agent <id> --print "<prompt>", and ran it. It was injectable, but only as a shell-exec function. An HTTP call to a model API, an MCP call to a skill server, or a webhook into an n8n workflow cannot pass for a shell command, so the seam was one level too low. Shell escaping, a 10 MB output buffer and a five-minute timeout were enmeshed in that one function as well.

I split it into a policy layer and a set of transports. The policy layer decides which harness and which provider a node gets. Each transport is encapsulated behind one interface and knows nothing about the others.

interface Executor {
  target: HarnessTarget
  run(input: AgentInput, target: HarnessTarget): Promise<AgentOutput>
}

type HarnessTarget =
  | "claude-code"   // CLI subprocess
  | "skill-server"  // MCP skill_invoke, or load-then-run
  | "headless-api"  // model API over HTTP
  | "n8n"           // webhook into a workflow
  | "desktop"       // stub, on purpose

// provider resolution, highest precedence first
node.provider → registry.defaultProvider → role default → harness default

The test I used for whether the seam was in the right place was mechanical. After the split, shell escaping, the exit-code-127 check for a missing CLI, the buffer size and the timeout each appeared in one file only, the CLI transport. None of it leaked back into the policy layer.

I wanted to decouple the model from the transport, so provider became a policy per role. There are four roles, reason, verify, synthesize and plan, and verify does not default to the model reason uses. A verifier sharing the worker's model, prompt lineage and context is a rubber stamp. Only one file in the source tree may name a model, and a test walks the tree and fails the build if any other file does.

The skill-server transport needed one extra move. Most of my skills declare no invocation model, so the skill server refuses to run them directly, and for a while every skill was selectable and none was runnable. The transport now attempts the direct call and, when it is refused, loads the skill's own definition and runs that on the CLI harness. The node still reports skill-server as its target, because that is what it asked for, and the definition that runs is the one it named.

Considered and set aside

  • Keep injecting at the shell-exec level. It would have forced every non-CLI transport to fake a command string, and the fakes would have drifted from the real transports within weeks.
  • Fall back to the CLI when a requested target is missing. An executor encumbered with a fallback runs the work on the wrong surface under the wrong provider and reports success. A missing target now throws at selection time, names what is missing, and touches no transport.
  • Build a desktop executor. Desktop stays in abeyance as a stub. Running an agent on a person's interactive session has no transport to test, since it means handing work to a human and waiting, and the approval gate already does that.

2. A verifier that is not the agent

The question: who decides that a node is done, and what are they allowed to see?

The verifier is interposed between an agent finishing and its record being written, so the record is gatekept by something other than the agent. It comes in three tiers, tried in order of cost.

What the verifier sees. It reads the files and judges the work, and the agent's account of the work does not reach it.

The deterministic tier comes first because it is the cheapest verdict available and the hardest to fool. A check that a file exists, or that it contains a structural marker, settles a large share of criteria with no model call. Before that tier existed, every attempt of every loop spent a model call to confirm things a filesystem read would have answered. The model tier runs next, under the verify role. The third tier is a person, the old approval gate reframed as a verifier whose verdict a human supplies, and that reframing is what later let autonomy become a slider rather than a switch.

// a node's verification spec: deterministic checks first, then criteria
{
  checks: [
    { kind: "file-exists", path: "timeline.fcpxml" },
    { kind: "contains",    path: "timeline.fcpxml", text: "<library" }
  ],
  criteria: ["narration drift against the planned scene total within 2%"],
  provider: { role: "verify" },
  threshold: 0.9,
  maxRetries: 1
}

Three smaller rules hold the verdict honest. The threshold decides, and a verifier returning “pass” with a score of 0.3 against a 0.8 threshold is overruled. An unavailable verifier, one that throws or returns unparseable output or has no criteria, returns a fail with a score of zero and the cause in its reasoning. The verdict also outranks the agent's self-report, in both directions.

That last rule came from a real run, and the run disabused me of the idea that having a verifier made its verdict authoritative. In a proposal-drafting loop, the drafter was killed by the harness timeout after it had written its file but before it printed its JSON summary. It self-reported failed. The verifier read the file and scored it 1.0, and the loop exited on a pass. The node-status function, embroiled in the older assumption, still checked the self-report first, recorded the node as failed, and paused the pipeline. The inversion the verifier existed to prevent was sitting one function downstream of it.

function resolveNodeStatus(outcome) {
  // the verdict is read first, whatever the agent said about itself
  if (outcome.verification)
    return outcome.verification.verdict === "pass" ? "complete" : "needs_review"
  // no verdict exists: a genuine failure skipped verification entirely
  if (outcome.output.status === "failed") return "failed"
  return outcome.output.status
}

needs_review carries its own meaning here. A node that ran and produced artifacts but missed its criteria has not met them, so it cannot be complete. It did run, so it has not failed. Keeping that middle state distinct is what lets the graph route on it later.

Considered and set aside

  • Let the verifier see the agent's summary. It would have made grading faster, and it would have engendered a reviewer that grades claims. Seven tests assert that the agent's summary, decisions and raw output are absent from the serialised verifier input.
  • Trust the verifier's own verdict field. Models return “pass” next to scores that do not support it. The runtime reads the score and computes the verdict itself.
  • Treat an unavailable verifier as a pass. An outage would then read as a clean run, and a clean run is what the autonomy ledger promotes on.

3. A loop that exits on a verdict

The question: what ends a loop, and what does the next attempt learn from the last one?

The counter became a ceiling rather than the exit condition, and the loop subsumed the old inline retry along the way. A loop stops when the verifier passes the work, and maxIterations only bounds how long it may keep trying, so a nine-iteration loop that passes on attempt two runs twice. Without the ceiling, a loop that cannot converge would run until its budget was depleted.

One loop node. The back-edge carries the verifier's objection, and every attempt stays on disk.
interface LoopSpec {
  goal: string
  verification: VerificationSpec   // the exit condition
  maxIterations: number            // a ceiling, not the exit
  onHalt: "return_best" | "escalate"
  stallWindow?: number             // opt-in
}

// what attempt n+1 is told about attempt n
retryContext = {
  previousAttempt: n,
  failureReason:   verdict.reasoning,     // the verifier's objection
  humanFeedback:   verdict.suggestedFix   // what to change
}

The feedback field had been declared on the retry context since the first version of the runner and written by nothing until the loop existed. Filling it changed what a retry is. The agent is told what the verifier objected to, rather than hearing its own excuse back. It needed one more fix before it worked, since the prompt builder did not surface the retry context to the agent at all, so early revisions were blind retries that happened to carry a better reason around unread.

Halting and failing are different outcomes here, and the two halt modes cover different kinds of work. return_best suits deadline-bound jobs, where a proposal at 94% coverage beats no proposal. escalate pauses the pipeline for a human, a state the engine and the resume path already understood. Returning the best attempt entailed keeping every attempt, so each one stays on disk under iterations/{n}/ with its verdict beside it and a loop-trace.json at the node root.

An agent that throws inside a loop becomes an attempt with a score of zero, and iteration continues. That attempt skips the verifier call entirely, since there is nothing to score and no reason to pay for a check. When two attempts tie on score, the earlier one wins, because the later one spent more to get to the same place.

Considered and set aside

  • A default stall threshold. Picking one would have shortened every loop in the system without anyone deciding it should. stallWindow is opt-in per loop.
  • Overwriting attempts in place. Cheaper on disk, and it makes return_best able to return only the best record, never the best files.
  • Letting the loop own pipeline state. On an escalating halt the loop returns a halt action and the engine writes the paused status. That kept the loop testable with no project directory and let the graph reuse it as a node unchanged.

4. A graph that walks a frontier

The question: what replaces the cursor, and where are cycles allowed?

Everything before the graph assumed a total order, an integer cursor walking a list. The frontier superseded it. A node is runnable when its predecessors have resolved and at least one of its inbound edges has fired, and a node named in convergence additionally waits for every predecessor.

const isRunnable = (id) => {
  if (resolved.has(id)) return false
  const ins = inbound.get(id)
  if (ins.length === 0) return entries.has(id)
  if (!ins.some(e => fired.has(e))) return false
  // a join waits for every branch, not the first one back
  if (convergence.has(id)) return ins.every(e => resolved.has(e.from))
  return true
}

The node itself is a union of three shapes, and all three run through one recursive entry point. If loops and graphs had been two engines calling each other, the abstraction would have been wrong, and the engine swap proved it. The old flat pipeline stopped being a second mode and became the degenerate plan, a straight line walked by the same code as everything else.

The composition rule. A graph node may be a loop, a loop step may be a sub-graph, and there is one engine.

Cycles are legal only through a loop node. A raw backward edge between ordinary nodes is a plan validation error, caught before the first model call, along with duplicate node ids, dangling edges, unreachable nodes, a plan with no entry node, and agents the registry does not know. Plans are data, and every structural mistake a plan can contain is cheaper to find before execution than halfway through a walk.

Edges carry guards, and the guard strings can come from a plan file, so evaluating them as code would be remote execution with extra steps. The guard language is circumscribed to one comparison over a fixed set of variables. A payload that is not a comparison does not fail evaluation, it never reaches an evaluator, and a test asserts that eval, new Function and dynamic import appear nowhere in the file.

// variables:  verdict | score | status | criteriaScores["key"]
// operators:  ==  !=  <  <=  >  >=    (ordering is numeric only)
// literals:   "string" | number | true | false
{ from: "validate", to: "direct", when: 'verdict == "pass"' }
{ from: "validate", to: "split",  when: 'status == "needs_review"' }

An unparseable guard does not fire its edge, and the walk logs that it did not. An ordering comparison on a string, "pass" < 0.8, is treated as a plan bug and declines rather than coercing. When no verifier ran on a node, the guard context reports the agent's status in the same vocabulary, so a plan can still branch on it without the runtime inventing a verdict it never produced.

Joins needed the most care. Without convergence, a diamond either runs its join twice or skips it, and neither shows up as an error. The mirror case is a branch nobody takes. When every inbound edge of a node has resolved and none fired, the node is marked skipped and the skip cascades, so a walk that declines every edge ends instead of hanging.

The reference workload was an article-to-video pipeline that already existed as a graph drawn by hand in prose, with seven stages, three quality gates, a conditional fork and a human in the loop. I chose it before the loop primitive existed, because a primitive built against a toy workload stays dishonest about what it cannot do. A script loop runs up to three attempts and escalates if it cannot clear its quality gate. A validator then either continues to a single video or proposes a multi-video split.

The fork in the reference plan. Two guarded edges leave the validator. Dashed nodes are sub-graphs with their own plans and their own autonomy policy.

The routing choice on that fork is the part I would defend hardest. The runtime's verdict is binary, and a proposed split is neither a pass nor a fail. I routed it on the validator's needs_review self-report, which already meant “a human must decide”, and a split is a human decision. Inventing a third verdict for one workload would have widened the guard language for every plan to serve one of them.

A few smaller decisions carry the rest of the weight. The node id became the primary key, since one agent can sit at two nodes and a record keyed by agent cannot express that. Output paths nest to match the execution tree, outputs/{parent}/{child}/, so the directory structure alone is enough to reconstruct a run. Resume replays completed nodes instead of re-running them, and re-fires their stored verdicts through the guards so the walk reaches the same frontier. An escalating node pauses the walk rather than sweeping it, leaving everything downstream on the frontier for the human who is being asked to look.

The division of labour between the walker and the engine settled into one principle. The walker decides what can run. The engine decides what should run. Input construction, output paths, approval gates, the pause on a failed agent and state persistence all arrive as hooks, and the walker knows none of them. In the old engine those decisions were interspersed through one long loop body.

HookWhat the engine answers through it
inputForNodeBuilds the agent input, including summarised upstream context and any retry context
executorForNodeBinds an executor to the node, or to attempt n of a loop node, so attempts land in their own directories
beforeNodeRuns the approval gate, which can run, skip or pause the node, with the enclosing sub-graph chain for clamping autonomy
afterNodePauses the pipeline when an agent fails outright
statePersists node records, the frontier and the linear projection older tools still read
completedSupplies records from a previous run, so resume replays rather than re-runs

Considered and set aside

  • Boolean operators in guards. One comparison per edge holds until a real plan needs two. Guessing at operator precedence before then is how small grammars rot.
  • Sweeping downstream nodes on escalation. Marking them skipped would discard the rest of the plan on the one path where a human is being asked to look at it.
  • A graph for every job. The planner defaults to a straight line and emits a fork only where the spec gives it a reason. A fixed graph is the wrong tool for exploratory work, where the next step depends on what the last one found.

5. Agents chosen by declaration

The question: how does the runtime pick an agent for a node without guessing?

The old registry was a set of filenames, and it could only ever say no. It deleted ids the router had already chosen from a hardcoded table. I replaced it with a contract whose fields delimit what each skill and agent is for, declared in its own frontmatter and read by a generator that does structured extraction only, with no model and no inference. What an author writes is what the index says, and what an author omits is absent.

purpose:       one line, what it produces
consumes:      artifact kinds it reads
produces:      artifact kinds it emits
depends_on:    surfaces it calls
exposes:       primitives it offers outside its own pipeline
capabilities:  [domain.verb-object]   # the dispatch key
triggers:      [phrases]              # discovery only

Two fields decide reachability, and I kept them apart on purpose. capabilities feeds dispatch, and only an exact match binds an agent to a node unattended. triggers feed discovery, surfacing candidates for a person or a model to choose between. Merging them would have made every trigger phrase a dispatch key, and a plan asking for a case study would auto-bind whatever agent happened to mention case studies. A capability counts as composable only when its entry declares what it consumes, produces and exposes, and coverage below that is reported rather than enforced.

The registry interleaved three sources, local agent files, the generated capability index and the skill server. A local declaration always wins, and later sources only fill gaps. An empty field means undeclared. An agent with no consumes has not said what it reads, which is different from reading nothing, and the runtime does not infer that an edge is feasible from a sparse entry. Reading absence as permission would make every compatibility check pass for the wrong reason.

The lexical matcher I built for discovery showed why dispatch had to stay strict. Asked for “test”, it ranked a study-abroad advisor first, because that agent's description mentioned standardised test planning. So the matcher shipped as substrate, and a weak match became a floor. When no agent declares a capability by its exact name, a human picks from the candidates, at every autonomy level.

The registry work also turned up the least visible bug of the build. The default verifier was an agent called qa-engineer, one of the five that existed only in documentation. Every verification spec that named no verifier resolved to an agent the executor could not load, and an unloadable verifier returns a fail with a score of zero. Verification degraded to “everything fails”, and nothing reported it. The registry document was transposed from something people wrote by hand into something the registry renders, so it has nothing left to drift from. The replacement verifier is domain-neutral, a real file, with a test asserting that it exists and that its definition names no domain.

This was the one place the no-edits rule broke, and it broke by design. The five phantom agents were pruned, and the archetypes that named them were deprecated. A retired archetype in an old project brief still loads, as a custom project with a warning naming what happened. Eleven tests asserted the retired behaviour, a six-step pipeline the runtime had not once been able to run, and those were the only tests I changed.

Considered and set aside

  • Scaffold files for the phantom agents. It would have made the pipeline look complete and filled five nodes with definitions nobody had designed.
  • Fuzzy dispatch. It would have ensnared the dispatcher in near matches, the confident-wrong case. It binds something adjacent, runs, and reports success on the wrong job.
  • Letting two ids share one identity. A duplicate id where either copy declares capabilities is a build failure that names both paths, because otherwise one wins silently on file-walk order.

6. A planner behind a gate

The question: if a model writes the plan, what is it allowed to put in it?

The decomposer takes a spec, a goal plus a list of verification criteria, and asks a model for a candidate graph. The model proposes and a deterministic gate disposes. The candidate is parsed as data and not executed, so a model that emits a hostile string cannot subvert the runtime through it, and nothing leaves the gate in a shape the runtime did not ask for.

From spec to a runnable plan. The model sits inside a dashed box because nothing it emits is trusted until the gate has handled it.

The gate's rules are delineated below, one per thing a model might try.

The model mayThe gate does
Name node idsReplaces them. Ids are gate-assigned, so duplicate, empty or hostile ids do not ship
Ask for a capability nothing declaresKeeps the node carrying the requested token and records a gap that names the namespace's real peers. code.migrate is not swapped for the adjacent code.simplify
Ask for a loopGrants it only where the spec's verifier declared that iteration is allowed
Write an edge guardKeeps it only if the guard grammar parses it
Propose a back-edgeDrops it. A loop is a node wrapping its own step, so a planner has no legitimate cycle to emit
Declare a joinKeeps it only with two or more live inbound edges
Return nodes with no usable edgesChains them in a line, the conservative default
Point a node at a missing verifierClamps it to the spec's first verifier, so no node ships unjudged

Two properties came out of that design. The same candidate, spec and declared capability set produce the same plan, byte for byte, which is what makes a decomposition reviewable, because a plan a person cannot reproduce is a plan a person cannot check. The gate also re-runs the ordinary plan validator on its own output and treats any finding as a defect in the gate rather than in the spec.

There is one sanctioned bypass. A spec can pin a capability to a named agent by hand, and that node ships already bound, because a human choosing an agent is a decision rather than a guess. Everything else goes through dispatch. The prompt already lists the declared capabilities, so the gate can look redundant, and the comment I left in that file answers it. A constraint stated in a prompt is a request, and a constraint enforced in the gate is a guarantee.

7. Autonomy as a ledger

The question: how much should a job be trusted to run without a person, and what moves that number?

The old approval mode had three fixed values and no memory. A manual project was gated on its thousandth run as hard as on its first, and an automatic one gated nothing however badly it was going. I replaced it with six levels, earned per job and recorded in a ledger that survives across runs.

LevelWhat gets gated
0Every node
1Every node, with the verifier's verdict shown to the human first
2Only the floor agents
3Anything after a failed verification or a halted loop earlier in the run
4Escalations only
5Nothing, except the floor

The policy and the ledger are separate modules. The policy is pure, taking a level and the run's signals and deciding whether a gate fires, with no state and no I/O. The ledger holds history. Levels three and four gate on signals from the run so far, because a gate consulted before a node runs cannot see that node's outcome.

How a run moves the slider. Trust accumulates slowly and is withdrawn at once, since the two mistakes do not cost the same.

The floor outranks the level. Agents on the floor list stay gated at every level including five, because an irreversible step, a deploy or a publish or a migration, is not made reversible by a good track record. No streak can greenlight a floor agent. A capability the dispatcher would not bind is the same kind of floor, and it gates at every level too.

The definition of “clean” was wrong in its first version. The bug was an unlooked-for consequence of a two-state outcome. I had collapsed every run that was not clean into an escalation, which meant a loop that converged on its second attempt, the retry primitive doing its job, cost the job a level. The more a job used the loop as designed, the faster it lost autonomy. The fix was a third outcome, decided in one function that the ledger reads rather than re-derives.

function classifyRun(state) {
  // escalations first: a real incident outranks everything else
  if (state.status === "paused_for_review")       return "escalated"
  if (anyNode(n => n.status === "failed"))       return "escalated"
  if (anyVerified(n => n.verdict !== "pass"))     return "escalated"  // waved through counts too

  // held: nothing earned, nothing broken
  if (verifiedCount === 0)                          return "held"       // no evidence either way
  if (anyVerified(n => n.firstAttempt !== "pass")) return "held"       // converged on retry

  return "clean"
}

A run with no verifier is held rather than clean, because without a verifier “clean” means “the agent said so”. A failure that a human waves through counts as an escalation, the same as an honest failure, or the gate becomes a way to launder a bad run. The classifier reads per-node records rather than the per-agent projection, because when two nodes share an agent the projection keeps only one of them, and promoting a job on half its story is the failure the whole ledger exists to prevent.

Three decisions about identity and scope finished it. The job key is the project path, the archetype and a canonical hash of the plan, so editing the plan resets the streak, since ten clean runs of a three-node plan say nothing about the six-node plan that replaced it. The ledger lives outside the per-pipeline state file, which is overwritten on every run, and outside version control, because a level earned on one machine's evidence should not travel to another checkout. A sub-graph runs at its parent's level or lower and inherits the union of the floors, so a nested graph declaring level five cannot circumvent its parent's gates.

Considered and set aside

  • Symmetric movement. Up one per clean run and down one per bad run treats a missed escalation and a missed promotion as equal costs, and they are not.
  • Storing the level in pipeline state. That file is minted fresh on every run, so an earned level would be erased by the next one.
  • Silently migrating old projects onto the slider. Legacy approval modes map to levels 0, 2 and 5 with the old gate list as the floor, and they write no ledger at all. Demoting a project that did not opt in would change behaviour nobody asked to change.

The whole runtime

Put together, the layers form one path from a written goal to a finished, judged run. Every arrow in it is a place where something is checked rather than assumed.

Declare, decompose, dispatch, walk, verify, record. The dashed return edge is the ledger, which changes how the next run of the same job is gated.

A few things remain open, and I would rather name them than let the diagram imply otherwise. Fan-out is static, so the reference plan materialises two per-video branches rather than one per video the split produced. Guards take one comparison. The token-count field on agent output is declared and still unpopulated, and loops are the one place where cost stops being predictable. Each of these has a slot waiting for it, which is the most a runtime can promise about work it has not done yet.

The walker changed little after the engine swap. What it gained later was an accretion of hooks, each one there to devolve a decision the walker deliberately does not make. The rules around it were rewritten more than once. The order of the node-status check, the default verifier and the meaning of a clean run were each wrong in a first version that passed its tests, and each of them was about who gets to say the work is done.
