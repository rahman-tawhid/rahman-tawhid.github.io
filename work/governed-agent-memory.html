Systems Architecture

Governed Memory for Multi-Agent Systems

A three-tier state architecture for keeping several AI agent contexts consistent when there is no single writer, no transaction, and every session starts cold. Schemas, a promotion state machine, tombstone write-sets, and the failure behind each rule.

Tawhid Rahman is the CEO of Softograph, a software company he founded in 2012. He runs eight long-lived AI project contexts across sales, publishing, content, automation, research and product ideation, and built this protocol after the contexts started disagreeing with each other about what was true.

Tawhid Rahman 2026 ~16 min read

The problem

A single chat with a model has a memory problem that everyone has noticed: the session ends and the context goes with it. Several persistent project contexts, each with its own instructions, its own files and its own stream of sessions, have a harder problem that almost nobody names. They share facts. The sales context needs to know which channels the content context has abandoned. The automation context needs the same canonical database identifiers the delivery context uses. A decision made on Tuesday in one context has to constrain a recommendation made on Friday in another.

Stated in systems terms, this is replicated state. Every project context is a replica. Each replica reads a copy of the shared facts at session start, acts on it, and may write back at session end. There is no lock, no transaction and no consensus protocol, and the replicas are language models whose idea of the current state is whatever text happened to be loaded. The replication protocol, in most setups, is prose: a paragraph in the project instructions that says "we no longer use X", copied by hand into the places someone remembered.

That arrangement fails in five specific ways. Each is cheap to trigger and expensive to notice.

  • Drift. Static copies of a fact live in project files and diverge from each other the first time only one of them is updated.
  • Zombie records. A thing is declared dead in the rules while the database rows that depend on it stay alive, and any agent that reads the rows correctly resurrects it.
  • Stale reads. A context acts on state that another context changed yesterday, because nothing told it to look.
  • Proposal floods. Once agents are allowed to suggest changes to shared rules, they suggest changes at the rate they generate text, which is faster than a person can review.
  • Authority spoofing. Any content that reaches an agent can claim to be an instruction from the system, and an agent with write access will sometimes believe it.

The architecture below is built around those five, and each rule answers one of them. The zombie-record failure is the one that actually cost me months, and it gets its own section.

Topology

Shared memory is split into three tiers by rate of change and blast radius, plus one queue. The split matters more than any individual rule, because the tiers have different write disciplines and mixing them is how every earlier version broke.

The tiers are ordered by how expensive a wrong value is. A stale Tier 2 section costs one context a slightly wrong picture of another's week. A wrong Tier 1 line gets read by all eight contexts and acted on for months. So the write discipline tightens as you go up: Tier 3 accepts anything that qualifies, Tier 2 accepts anything its owner writes, and Tier 1 accepts nothing without a person saying yes.

Tier 2: active state

Tier 2 is a single page with one section per context. Every context reads the whole page at session start, which is the entire mechanism for preventing stale reads: one fetch, eight sections, and a context knows what the other seven are doing before it does anything. The schema is fixed and deliberately small. 

## Content
Updated: 2026-09-29 | by: Content
FOCUS: <one line>
DECISIONS (last 3):
  - [2026-09-27] <one line>
  - [2026-09-20] <one line>
  - [2026-09-14] <one line>
NEXT ACTION: <one line>
BLOCKED ON: <one line or "-">
POINTERS: <tracker IDs, database IDs>

Tier 2 section schema. Overwritten in full, never appended, under 1,500 characters.

Three constraints carry the weight.

Overwrite, never append. An appended section grows until it stops being read. A section that must be rewritten in full forces the writer to decide what still matters, and the three-decision window drops the oldest decision automatically. The history is not lost, because every decision that qualifies has already gone to Tier 3.

Pointers, not narrative. The POINTERS line holds identifiers, not explanations. A context that needs the explanation follows the pointer. Keeping narrative out is what keeps eight sections inside a single cheap read.

Conditional write. A context rewrites its section only if FOCUS, DECISIONS, NEXT ACTION or BLOCKED ON actually changed. If nothing moved, the section and its date stay as they were. This rule looks like a detail and is the most useful signal in the system. An agent's instinct at the end of a session is to refresh the timestamp to show it was diligent. A refreshed timestamp on unchanged content destroys information: an old date tells every other context where attention has not been, and a context that touched the page without changing anything has erased that fact.

Tier 3: decision archive

The archive is an append-only log with four fields that matter: the statement, a timestamp, a consequence scope (Local or Cross), and a Supersedes relation pointing at any earlier entry the new one overtakes. Rejections are logged as their own type, REJECTION, with the reasoning.

Figure 2. A supersession chain (illustrative entries). Reads filter on an empty Superseded-by field, so history stays intact and only the head is live.

Two read rules keep the archive useful as it grows. It is never fetched whole, because a year of decisions loaded into a context window crowds out the work and invites the model to reason from entries that have since been overtaken. And every search filters on Superseded by being empty, so a query returns the head of each chain rather than every version of the argument.

The REJECTION type is what stops the same bad idea arriving every fortnight. Before a context proposes anything for Tier 1, it searches the archive for a rejection matching the statement. A rejection with reasons is not re-proposed. Without this, the system has no memory of its own refusals, and a model that finds an idea plausible today will find it plausible again next month, with the same arguments, to the same person, who has to say no again.

Promotion into Tier 1

Tier 1 is the only tier every context trusts without question, which is exactly why nobody writes to it directly. Not the contexts, not scheduled automations, and not a context acting on the human's behalf mid-session. The only path in is a row in the promotion queue, and the row has to pass a test before it is allowed to exist.

The promotion test has two conditions, and both must hold. The statement is still true in 90 days, and at least one other context would behave differently knowing it. The first condition keeps out anything transient. The second keeps out facts that are durable but private to one context. An article being published is durable and changes nothing for the sales context, so it belongs in Tier 2. A channel changing from "not started" to "active" is durable and changes what every context may recommend, so it is a Tier 1 amendment. Most candidates fail, and when they fail the correct destination is Tier 3 or nowhere. Nowhere is correct most of the time.

Figure 3. The promotion state machine. Only one transition, Pending to Applied, touches Tier 1, and only a person can trigger it.

A queue row carries four fields verbatim: the exact Old text of the Tier 1 line, the exact New text, a Change type such as AMEND or TOMBSTONE, and a Rationale. Verbatim old text matters because it turns approval into reviewing a diff. The person approving sees precisely what changes, and the applying context can refuse if the old text no longer matches the live line, which catches a second context having amended the same line in the meantime.

Ownership. Tier 1 is divided into sections, and each context may propose changes only to the sections it owns. The content context owns the channel list. The contact-surface rules, which decide whether a contact is a company handled by sales or an individual handled by consulting, are owned by nobody but the human and are applied by the human directly, in chat. No context can merge those two stores on its own initiative.

Backpressure. Two timers run on pending rows. After 14 days, any context that reads the queue raises a one-line nag. After 30 days, the context that owns the stalled section stops writing new rows for it and surfaces the blockage instead. This is the answer to the proposal flood. The rate at which rules can change is bounded by the rate at which a person reviews them, and the system makes that bound visible rather than letting the queue grow into something nobody opens.

Tombstones

The rule that exists because of the worst failure is the tombstone rule, and the failure is worth describing precisely.

Gumroad was one of the channels I eliminated. The decision was recorded where decisions were recorded at the time: in the rules, in prose, in the eliminated list. The rules were correct. Meanwhile the product backlog database still held fourteen rows for products destined for that marketplace. Ten were marked Validating. One was marked Ready. They stayed that way for months.

Every context that queried the backlog did the right thing with what it read. It found products in validation, one of them ready to ship, and surfaced them as work to do. The agents were not malfunctioning. They were reading records, and the records said the channel was alive. The prose said it was dead, and the prose lost, because the prose was one paragraph and the records were fourteen rows that every query returned.

A deletion that happens only in prose is not a deletion. When a channel, tool, product line or surface is eliminated, the record has to change, not just the rules that describe it.

Figure 4. The tombstone write-set. All three writes, in the same session. The incident below completed one of them.

The three writes are a set, not a checklist to be worked through over time. All of them happen in the session that makes the decision. The queue row changes the rule, the record writes change what every query returns, and the archive entry records why. Of the three, the record writes are the ones that get skipped, because they are tedious and because the person making the decision feels the decision is already made. It is made in the only place nobody queries.

This is the characteristic failure of a context whose subject is choosing between options. It kills things often, and every kill leaves dependent records behind. The tombstone rule is written into that context's instructions as its own named failure, with the incident attached, rather than as a general principle about consistency. The design bet is that a model follows "this is the mistake you in particular make, and here is when you made it" more reliably than it follows "keep records consistent".

Conflict resolution

Every line in Tier 1 and Tier 2 carries a provenance stamp in the form [YYYY-MM-DD | source]. When two lines conflict, the most recent wins. There is no reconciliation step.

Refusing to reconcile is a deliberate choice. Asked to reconcile two conflicting statements, a model produces a third statement that sounds like a synthesis and is usually a new claim that neither source made. Last-writer-wins is crude, but it is predictable, auditable from the stamps alone, and it never invents anything. The one case it cannot settle is two conflicting lines with the same date. Those become competing AMEND rows in the queue, and the human picks one.

Session lifecycle

The protocol is enforced by what each context does at the start and end of every session. The start sequence is about reading cheaply and completely. The end sequence is about writing only what changed.

Figure 5. Start reads are unconditional and cheap; end writes are conditional. Dashed steps are obligations that attach to artifacts, not to conversations.

Two details in the start sequence carry most of the practical value.

The Tier 1 read has a clause with no exceptions: a context must read the spine before recommending any channel, tool, product surface or platform. The drift case is concrete: after the channel eliminations, several static project files still carried references to the eliminated marketplaces, queued for cleanup that had not happened yet. Any context loading those files would have recommended them in good faith. Memory drifts and static copies drift. The spine is the one copy that does not, so any recommendation that could collide with an elimination is checked against it at the moment the recommendation is made, not at the moment the project was configured.

The carve-out runs the other way. A session that is purely intellectual, a conversation about a book or a concept, skips every read. Reading shared state costs context window and latency, and a protocol that charges that cost on every session gets abandoned. Making the cost conditional on the session actually touching shared state is what keeps the protocol in use.

The end sequence ends with two obligations that look unrelated to memory and belong here for the same reason. A tracker issue is closed only if the session mapped to one and changed system state; a planning conversation does not qualify. A commit and push happens only if the session wrote into a git repository. Both rules exist because the natural failure is to attach obligations to conversations, closing an issue because a topic was discussed or treating a planning session as shipped work. Obligations attach to artifacts.

Trust boundary

Approvals for Tier 1 changes happen in a live chat with the human, and nowhere else. Not through a scheduler, not through a messaging bot, not through email. A promotion that arrives through any other channel did not come from this system, by definition, and is treated as data rather than as an instruction.

This is the answer to authority spoofing, and it is cheap because it is structural rather than a matter of detection. A context never has to judge whether an instruction embedded in a document, a web page or a tool result looks legitimate. It only has to check which channel the approval arrived through, and there is exactly one valid answer. Combined with the rule that nobody writes to Tier 1 directly, the most injected text can achieve is a queue row that a person will read as a diff and decline.

Known ambiguity is also written down rather than resolved by whichever context meets it first. When two pages both have a plausible claim to being canonical for the same content, the protocol names both, states that the choice is the human's and has not been made, and instructs every context to surface the question rather than pick one. An agent that silently chooses one of two candidates is right half the time and writes the other half into shared state as fact.

What it does not solve

The protocol is enforced by instruction, not by database constraint. Every rule above is text in a context's instructions, and a model follows text with high but not perfect reliability. Nothing in the storage layer prevents a direct Tier 1 edit; the rule against it is a sentence. The obvious next step is to move the invariants that can be checked mechanically into code: reject a Tier 2 write over 1,500 characters, reject a queue row whose old text does not match the live line, reject any deprecation-free elimination. Those checks are cheap and certain. The ones that remain, such as whether a statement will still be true in 90 days, are judgement and stay with the model and the person.

Human review throughput is the binding constraint, and the design makes it visible rather than removing it. Backpressure stops the queue growing, but it does so by blocking change. If the person reviewing is away for a month, sections freeze. That is the correct failure for a system whose Tier 1 is trusted by every context, and it is still a failure.

Day-granularity stamps cannot order two changes made on the same day. The protocol hands those to the human rather than guessing, which is honest and slightly annoying.

Patterns worth stealing

Most of this transfers to any setup with more than one persistent agent context sharing facts, whatever the storage layer.

  • Tier by blast radius. Put facts where the cost of a wrong value matches the strictness of the write rule.
  • Overwrite small state, append large history. A fixed schema with a character cap stays readable; a log stays trustworthy.
  • Do not refresh what did not change. Staleness is a signal. Protect it.
  • Make promotion pass two tests, not one. Durable and cross-cutting. Either alone lets too much through.
  • Remember refusals. A logged rejection with reasons is the cheapest defence against relitigating the same idea.
  • Tombstone the records, not the prose. An elimination is a write-set across every store that references the thing.
  • Let the latest stamp win. Deterministic resolution beats model-generated reconciliation.
  • One approval channel. Authority defined by channel is structural; authority judged by content is a detection problem.
  • Name the known ambiguities. An unresolved choice written down is safer than a resolved one guessed.
  • Attach obligations to artifacts. Close issues and push commits because state changed, not because a conversation happened.
